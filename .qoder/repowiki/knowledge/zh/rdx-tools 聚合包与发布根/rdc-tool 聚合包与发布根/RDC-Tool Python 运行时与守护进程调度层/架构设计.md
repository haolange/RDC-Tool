模块以 `rdc_tool` 包为核心，按职责划分为四层：
- CLI 入口层：`cli.py` 解析 `rdc-tool` 命令并委托给 `daemon.client`；`server.py` 在 daemon 模式下通过 `__getattr__` 延迟加载 `server_runtime`，暴露 `dispatch_operation` 作为统一异步入口。
- 守护进程层（`daemon/`）：`server.py` 的 `DaemonRuntime` 基于 `multiprocessing.connection.Listener` 监听 Windows named pipe（`\\.\pipe\{pipe_name}`），负责鉴权 token、心跳与 lease 管理、上下文状态持久化到 `daemon_state.json`；`client.py` 通过 `Client` 发起请求、启动/停止守护进程并处理启动锁（文件锁 + 内存 mutex）；`worker.py` 封装子进程 `RuntimeWorkerProcess`；`ownership.py` 通过 `OwnerLease` 实现多进程 owner 互斥。
- 运行时服务器层：`server_runtime.py` 是真正的服务端实现，从 `spec/tool_catalog.json` 注册工具、维护 `SessionManager`/`PreviewWindowHost`/`EventGraphService`/`RenderService`/`PipelineService`/`PerfService`，并通过 `CoreEngine` + `operation_registry` 执行 `rd.*` 操作，产出带 `ok/data/artifacts/error/meta` 的标准信封。
- 核心服务层（`core/`）：`engine.py`、`session_manager.py`、`render_service.py`、`pipeline_service.py`、`perf_service.py`、`event_graph.py`、`patch_engine.py` 等各自专注一个领域，被上层通过构造注入依赖。
依赖方向自顶向下为 CLI → daemon client/server → server_runtime → core/*，所有跨进程通信经由 named pipe 序列化 JSON，状态通过 `runtime_paths.cli_runtime_dir()` 下的 JSON 文件与 `context_snapshot`/`runtime_worker_state` 持久化。
